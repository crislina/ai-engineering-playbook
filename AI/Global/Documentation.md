# Documentation

## Purpose

Keep project knowledge discoverable and current.

## Documentation Rules

- Update docs when behavior, setup, workflows, or public interfaces change.
- Prefer examples for setup and usage instructions.
- Keep docs close to the code or decision they describe.
- Remove stale guidance instead of layering new text over old assumptions.

## README

- Explain project purpose, setup, and common workflows.
- Keep quick-start instructions current.
- Link to deeper architecture, API, and decision documents.

## Architecture Documentation

- Record major boundaries, layers, dependencies, and trade-offs.
- Update architecture docs when architecture changes.
- Reference decisions from `AI/Project/Decisions.md`.

## API Documentation

- Document endpoints, request shape, response shape, errors, status codes, pagination, and versioning.
- Include examples for important workflows.
- Keep public behavior consistent with implementation.

## Decision Log

- Record why meaningful decisions were made.
- Include rejected alternatives when the reason matters.
- Capture consequences and future review triggers.

## Future Enhancements

- Track ideas that are useful but not in current scope.
- Separate confirmed roadmap items from speculative improvements.

## Known Issues

- Document limitations, defects, and operational risks.
- Include workaround, severity, owner, and target fix when known.
